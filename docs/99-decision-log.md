# 99 — Decision Log (ADRs)

Format per playbook: **Options considered → Choice → Justification → Revisit when**. All decisions reviewed and accepted by owner 2026-11-12.

> **Phase context** — Phase 1 = local Docker Compose (current build target). Phase 2 = AWS cloud deployment (later stage). Decisions reflect the Phase 1 starting point and document the Phase 2 upgrade path.

| ID | Decision | Options | Choice | Justification | Revisit when | Status |

| ADR-01 | Agent topology | Single agent; supervisor-worker; full orchestrator | Guard→Router→**Supervisor + sub-agents**, deterministic fixed pipelines for simple paths | Different tools/prompts per domain; keep prompts small; fast cheap path for simple doc Q&A expected to be ≥50% of traffic | <3 task types or prompts stay tiny → collapse to single agent | Accepted |
| ADR-02 | LLM provider access | Bedrock; direct Anthropic API; OpenAI; Ollama (local) | **LiteLLM proxy** — provider selected via `LLM_PROVIDER` env var; default Anthropic API; local dev can use Ollama for zero-cost offline runs | Provider-agnostic unified API surface; switch provider without code change; portfolio demonstrates multi-provider AI engineering; Ollama enables free local dev and offline demo | — | Accepted |
| ADR-03 | Model routing | One model; routing | **Fast/cheap class** (Claude Haiku, GPT-4o-mini, or small local model) for guard/rewrite/routing/summary; **capable class** (Claude Sonnet, GPT-4o, or large local model) for supervisor/sub-agents; active provider + model names are config | Tier routing preserved across all providers; LiteLLM normalises provider differences; free local path via Ollama small/large model pair | Fast-class accuracy falls on routing eval | Accepted |
| ADR-04 | Vector store | Aurora+pgvector; OpenSearch; Pinecone; Qdrant | **Dual store: Qdrant** (enterprise data — unlimited scale, purpose-built filtered-ANN) + **Supabase pgvector** (personal docs — hybrid search + RLS); **Supabase PostgreSQL** replaces Aurora for all relational data | Qdrant outperforms pgvector on filtered-ANN recall at large enterprise chunk counts; Supabase free tier eliminates Aurora cost entirely; both run locally (Docker + Supabase CLI); single Supabase PG instance covers RLS, metadata, audit, chat history, run state | Qdrant → Qdrant Cloud managed at scale; Supabase → self-hosted for cloud if cost warrants | Accepted |
| ADR-05 | Retrieval strategy | Similarity only; hybrid; hybrid+rerank | **Hybrid (vector+BM25-style) with RRF + multi-query rewrite; rerank optional** | Exact terms (IDs, names, codes) need keyword; semantics needed for concepts; rerank adds latency and is off by default | Eval shows recall@5 gain from reranking justifies latency cost | Accepted |
| ADR-06 | Knowledge approach | RAG; fine-tune; long context | **RAG** — enterprise chunks in Qdrant; personal doc chunks in Supabase pgvector | Frequent doc updates, per-document ACLs, citations; dual store splits concerns cleanly: Qdrant for unlimited-scale enterprise, Supabase pgvector for personal docs with RLS integration | — | Accepted |
| ADR-07 | Text-to-SQL accuracy | Raw schema prompt; curated semantic catalog; fine-tuned model | **Curated catalog + metrics + examples + AST validation + self-correction (max 3)** | Most SQL errors are semantic ambiguity, not syntax; catalog addresses the root cause | Catalog upkeep cost too high → switch to auto-generated catalog + human review pass | Accepted |
| ADR-08 | DB access isolation | Agent connects directly; dedicated gateway | **Data Gateway service** with read-only creds, re-validation, row caps, central audit | Credentials and network path confined to one service; agent workers never see DB credentials | — | Accepted |

| ADR-10 | Code execution sandbox | Run in worker; Fargate task; Lambda; Docker subprocess | **Phase 1: restricted Docker subprocess** (no network, scoped temp volume, `--network none`); **Phase 2: Lambda container, no egress, STS-scoped S3** | Phase 1: Docker already in stack, strong isolation via network-disabled container, zero infra overhead; Phase 2: Firecracker MicroVM, instant scale, no idle cost | Need GPUs or long jobs (>15 min) → Fargate task | Accepted |
| ADR-11 | Charts | Server PNG; Plotly JSON; Vega-Lite | **Vega-Lite spec built by tool, rendered client-side** | Interactive, schema-validatable, data-bound (numbers come from tool results not LLM imagination); exportable PNG/SVG | Need complex custom viz → Plotly | Accepted |
| ADR-12 | Streaming | WebSocket; SSE; polling | **SSE with seq-numbered events from Redis Streams, resumable via Last-Event-ID** | Simple unidirectional; works through any reverse proxy (Nginx locally, ALB+CloudFront in cloud); run survives browser disconnect; resume gives gapless replay | Need bidirectional realtime (e.g. HITL confirmations) | Accepted |
| ADR-13 | Run execution | In API process; separate workers | **Separate Celery agent-workers** consuming from Redis; Supabase PG run table; sweeper periodic task | Deploys and scales independently; no lost runs on API restart; LangGraph checkpoints in Supabase enable resume at node boundaries after worker crash | Redis round-trip overhead >50 ms proves problematic | Accepted |
| ADR-14 | Async jobs | Celery+Redis; SQS+ECS; Step Functions | **Celery + Redis** (Celery beat for scheduled maintenance; Celery workers for ingestion; retry + Redis dead-letter set as DLQ) | Python-native; Redis already in stack for SSE event bus; zero infra locally; docker-compose scales workers; portable to ECS Fargate for Phase 2; SQS can replace Redis as the Celery broker in cloud for durability | Cloud phase at scale → SQS as Celery broker | Accepted |
| ADR-15 | Conversation state | In-memory; Redis; PG | **Redis (hot/streams + Celery broker) + Supabase PostgreSQL (truth)** | Redis for fast shared state, SSE event bus, rate-limit counters, Celery task queue; Supabase PG for durable chat/run history, audit log, usage ledger; both run locally (Docker Redis + Supabase CLI) | — | Accepted |
| ADR-16 | Compute platform | Docker Compose; EKS; ECS Fargate; Lambda | **Phase 1: Docker Compose** (local, all services); **Phase 2: ECS Fargate** (cloud) | Phase 1: zero cost, full service topology mirrored locally, complete portfolio demo without cloud spend; Phase 2: ECS Fargate — demonstrates pragmatic enterprise-grade container orchestration, right-sized for the scale, low ops overhead, good architectural judgment | >100 services or advanced scheduling need → EKS | Accepted |

| ADR-23 | Multi-tenancy | Single tenant; multi-tenant | **Single tenant, `org_id` columns present** | Faster to ship; `org_id` columns make future upgrade cheap; RLS policies can be enabled when needed | SaaS plans or second customer org | Accepted |
| ADR-24 | Observability | LangSmith; Langfuse; CloudWatch only | **Langfuse OSS** (Docker Compose, free) for LLM traces + evals; **Prometheus + Grafana** (Docker Compose, free) for infra metrics; **CloudWatch** added in Phase 2 for AWS resources | Free stack; runs locally alongside services in docker-compose; Langfuse provides impressive LLM trace/eval UI for portfolio demos; no data leaves local machine; LangSmith free tier is a fallback for LLM traces | Cloud phase ops burden → Langfuse Cloud managed | Accepted |
| ADR-25 | IaC / local orchestration | Terraform; CDK; docker-compose | **docker-compose.yml** for Phase 1 (local); **Terraform + GitHub Actions** for Phase 2 (cloud) | docker-compose gives zero-cost full-stack local dev and demo; Terraform provisions cloud infra when ready; both live in repo demonstrating both skills | Team prefers CDK → swap Terraform for CDK in Phase 2 | Accepted |
| ADR-26 | Local object store | MinIO; SeaweedFS; Garage; LocalStack | **SeaweedFS** (`chrislusf/seaweedfs`, S3 API on :8333) behind the `ObjectStore` port | MinIO withdrew its public Docker images (Docker Hub and quay gated, repo archived 2026) so it is no longer pullable; SeaweedFS is actively maintained on Docker Hub, single-container, and S3-compatible — code talks only S3 protocol so Phase 2 swaps to real S3 unchanged | SeaweedFS S3-compat gap found in testing → Garage | Accepted |
| ADR-27 | Phase 2 RAG scope cuts | Presigned PUT vs API-proxied upload; `unstructured`/`docling` vs light parsers | **API-proxied multipart upload (≤ `MAX_UPLOAD_MB`, SHA-256 server-side) + `pypdf`/`python-docx`/text parsers behind a `Parser` port** | Presigned PUT needs SeaweedFS CORS config and a two-step client flow for no local benefit; light parsers keep the worker install small and Windows-friendly. Both sit behind ports (`ObjectStore`, `Parser`), so swapping is local to one module. Enterprise docs are visible to all users until groups exist; retrieval runs whenever the user has READY docs (no router until Phase 3) and grounds only above `RAG_MIN_SCORE` unless docs are explicitly selected | Uploads > 25 MB or scanned PDFs needed → presigned PUT + `unstructured` OCR | Accepted |
| ADR-28 | Agent worker runtime (Phase 3) | LangGraph PG checkpointer vs none; Celery solo / per-thread loops / one shared loop | **No checkpointing; Celery thread pool feeding one shared asyncio loop; watchdog per run** | LangGraph's Postgres saver needs psycopg async, which doesn't run on Windows' default loop, and runs are ≤ 120 s; instead a stale-run check (no heartbeat 60 s / queued 5 min) fails orphaned runs on the next send. Per-thread event loops hung because LiteLLM caches one HTTP client per process and it is bound to the loop that created it; a single loop thread owns every async client and Celery threads submit runs to it. A watchdog task cancels the graph on Stop or at `AGENT_MAX_SECONDS + 30 s`, so a hung provider call can't pin a run | Runs > 2 min or crash-resume needed → checkpointer on Linux workers | Accepted |
| ADR-29 | Default model tiers | Keep gpt-4o-mini / gpt-4o; GPT-5 nano/mini; GPT-6 luna / terra / sol | **fast = `gpt-6-luna`, capable = `gpt-6.1-terra`, both `reasoning_effort=none`; fallbacks gpt-4o-mini / gpt-4o** | `evals/model_bench.py` on EagleEye workloads (2026-11-12, models run sequentially): guard 39/40 vs 38/40 at $0.052 vs $0.072 per 1k calls (+0.2 s); grounded answers + tool plans 12/12 vs 12/12 at $0.54 vs $1.10 per 1k (+0.4 s TTFT). Reasoning models reject `temperature≠1` unless reasoning is off and bill thinking tokens by default, so the gateway sends `reasoning_effort` per tier and temperature only when accepted. gpt-6-luna also scored 12/12 on the capable set at $0.05 per 1k but is the smallest model; re-test for capable once the Phase 4 SQL golden set exists. gpt-6.1-sol can't disable reasoning and costs the same as gpt-4o | SQL golden set shows luna ≥ terra → capable = luna; latency becomes the bottleneck → re-benchmark | Accepted |
| ADR-30 | Phase 4 SQL access model | Group grants + `row_filter_sql`; DB-native RLS; role grants | **Grants per user role (`source_grants.role`): allowed tables + `can_see_pii`; the gateway re-validates every statement with a policy it builds from the role read from the DB; seeded demo Postgres warehouse (:5433) as the "enterprise DB"** | Groups don't exist yet (C2), and roles already drive every other permission. The gateway trusts only a 30 s HMAC token `{user_id, source_id}` and re-runs `sqlsafe`, so a compromised worker or prompt can't widen access. The read-only DB role with no `hr` grant is the last layer. A seeded warehouse lets the phase be reviewed with no customer data. **Follow-up to ADR-29:** on the SQL golden set (2026-11-13), luna matched terra (25/25 accuracy, 5/5 refusals) at a tenth of the cost and 0.4 s faster p50. **Approved 2026-11-13: capable = `gpt-6-luna`, capable fallback = `gpt-6.1-terra`** (replacing gpt-4o); terra remains one env var away (`MODEL_CAPABLE=gpt-6.1-terra`). A separate complex-task tier (e.g. `MODEL_COMPLEX`, escalating supervisor/complex or repeated SQL failures to terra) is deferred until evals show luna underperforming | Row-level entitlements needed → `row_filter_sql` / DB RLS; groups land → grants per group; real source onboarded → `dsn_env` + onboarding CLI | Accepted |
| ADR-31 | Phase 5 analysis sandbox & charts | Separate analysis worker; in-process DuckDB; Docker container per execution. Charts as artifacts vs in the message. Vega-Lite vs Plotly vs PNG | **Docker container per execution, started by the agent worker through an `AnalysisExecutor` port** (`--network none --read-only --cap-drop ALL --no-new-privileges --pids-limit 64`, memory/CPU caps, non-root, inputs read-only, one writable output dir, hard timeout). DuckDB SQL preferred, Python (pandas/scipy/sklearn) when needed; static checks (sqlsafe with a DuckDB policy; AST allow-list) are a convenience — **the container is the control**. **Charts: the model sends an intent (type, columns), code aggregates the data and builds a Vega-Lite spec with no colours/expressions, stored in the message part** (not an artifact); the frontend themes and renders it with vega-embed's AST interpreter (no eval). Datasets = uploaded CSV/TSV/XLSX → Parquet + DuckDB profile; any owned table artifact is an analysis input | A separate worker adds a queue hop for runs that are already ≤ 240 s; in-process DuckDB/pandas would run model code in the worker. The escape corpus (no network, read-only root, fork bomb, memory hog, infinite loop) passes against the real image. Charts are cheap to rebuild from their source artifact, so a message part avoids another table and endpoint. On the 16-case analysis golden set (2026-11-13) luna matched terra 15/15 + 1/1 at ~1/13 the cost, so analysis stays on the capable tier = luna. Deferred: enterprise datasets, doc-table extraction, uploads > 25 MB, box/heatmap/pie charts, forecasting, join-key helper (prompt asks for match-rate reporting instead) | Cloud phase → Lambda executor behind the same port; concurrent analysis load → dedicated worker queue | Accepted |
| ADR-32 | Phase 6 operations, accounts & retrieval chunking | Monitoring: Grafana/Langfuse vs an in-app admin console. Controls: feature flags in config vs Redis kill switches. Accounts: Clerk self-signup + lazy provisioning vs admin-provisioned. Chunking: 2400/3000 (A), 1200/1600 (B), B + PDF slide markers & bullets (C), C + Title Case headings (D) | **In-app admin console** (admin role re-read from the DB on every call; aggregates cached 60 s; read-only queries on the admin path only, nothing added to answer generation). **Redis kill switches** `kill:{chat,sql,analysis,uploads}` (fail open, audited before they change). **Admin-provisioned accounts only**: admins add users (one or CSV) → Clerk account + company Clerk organisation + EagleEye row; the API refuses any Clerk account it did not provision; delete = revoke the Clerk sign-in + status `deleted` (billing/audit kept, re-adding reactivates). Sign-in = custom page (Google, or username/email → password or emailed code). **Chunking = C**: 1200 soft / 1600 max / 200 overlap / 400 min, PDF slide markers ("Slide 3 of 12", "SLIDE 137: Title") and bullet glyphs as split points; Title Case headings off | One console instead of new infrastructure locally; kill switches act in seconds without a deploy. Server-side refusal makes "no self-signup" hold even if Clerk's sign-up setting is left on. Retrieval eval (`evals/retrieval_eval.py`, 10 fixture docs / 150 questions, 100 dev + 50 held out, query rewriting off, recall measured inside a 6,000-char context budget so big chunks don't win by size): dev A 0.79 / B 0.83 / **C 0.85** / D 0.84 → C chosen on dev, confirmed on held-out (C 0.88 vs A 0.82); all 150: budget recall **0.86 vs 0.79**, recall@5 0.87 vs 0.83, MRR 0.73 vs 0.69. Old 3000-char chunks were cut to 2,000 chars at retrieval, hiding their tails from the model. Spot check on a real slide PDF: 0 → 21 of 22 chunks carry a slide heading; D found 41 "headings" there including a footer author name and wrapped title fragments, confirming the misfire risk | Cloud phase → CloudWatch/Grafana alongside the console; synthetic corpus is easier than real documents → add real (non-private) documents to the eval set; scanned PDFs → OCR | Accepted |
